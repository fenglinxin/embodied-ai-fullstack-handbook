> 副标题：从采集落盘到可训数据集的端到端流水线——事件驱动、幂等重跑、数据版本与血缘一次讲清。

## 📌 开篇钩子

数据量到 5000 条时，团队通常会迎来第一场"数据事故"：工程师 A 手工跑清洗脚本，忘了加最新规则；工程师 B 用旧代码重新转换了 2TB 数据，把新格式覆盖了；训练时发现评测集混进了训练集——因为"当时手滑切错了文件夹"。

5000 条还能靠人肉救场，5 万条时人肉就是灾难。具身数据的生命周期很长：**采集 → 同步 → 清洗 → 去重 → 脱敏 → 评分 → 打包 → 发布 → 迭代**，每一环都是手工操作，出错概率随环节数量指数上升。

本章把数据管理从"手工活"升级为"流水线工程"：**事件驱动怎么触发、每个环节怎么保证可重跑、数据版本与血缘怎么管理、训练集发布怎么设门禁**。目标是让"数据从采集到训练"全程可追踪、可重放、可审计。

## 一、章节定位与适用人群

**章节定位**：数据层（数据工程的"工厂化"改造）。解决的核心问题：**手工管理导致错版本、脏数据、不可复现、事故频发**。

**适用场景**：个人学习 ☑ 科研实验 ☑（从脚本起步）企业开发 ☑（重点）产品量产适配 ☑（必须）
**建议阅读时长**：13 分钟（建议收藏，改造数据流程时对照）

**读完你将能**：
1. 画出自己数据管线的 DAG（有向无环图），识别手工断点；
2. 用"幂等 + 版本化 + 血缘"三原则设计可重跑流水线；
3. 建立训练集发布门禁，杜绝"脏数据悄悄上线"。

## 二、大白话原理：流水线要解决的三件事

### 2.1 数据不是"被处理"，而是"被加工成可追溯的资产"

想象工厂流水线：原料（原始采集）→ 每道工序（清洗/去重/标注）→ 质检（质量分）→ 包装（数据集版本）→ 出厂（发布训练集）。工厂和手工作坊的区别不是设备多贵，而是**每件产品都能查到来料批次和加工记录**。

### 2.2 三个设计原则

1. **幂等**：同一输入 + 同一版本代码，重跑 N 次结果完全一致——出错随时重跑，不怕跑一半；
2. **版本化**：数据、代码、规则、配置全部版本化，任何产物都能说清"由什么生成"；
3. **血缘**：从训练集能一路追溯到"哪批采集、哪条规则、哪个版本转换"——出问题三分钟定位。

> 💡 金句：**手工流程里，错误是随机的；流水线里，错误是可复现的——而可复现的错误，才修得掉。**

## 三、选型对比：流水线用什么搭

| 方案 | 定位 | 优点 | 局限 | 适合 |
| --- | --- | --- | --- | --- |
| Shell + Makefile/脚本编排 | 起步 | 零依赖、透明 | 无调度/监控/失败重试 | <1 万条、单人 |
| Python 脚本 + 任务编排（如 Airflow/Prefect/Dagster） | 企业数据工程 | 调度、重试、监控、DAG 清晰 | 运维成本、学习曲线 | 持续采集、多人协作 |
| 数据版本工具（如 DVC）+ 云存储 | 数据版本/血缘 | 与 Git 工作流一致、回滚方便 | 大文件/频繁采集需设计 | 科研与中小团队 |
| 全托管 ML 平台数据模块 | 一体化 | 省运维 | 绑定平台、成本高 | 有平台预算的企业 |

**选型结论（工程默认路径）**：
- **科研/单人**：Makefile 或轻脚本 + DVC 起步，先把"可重跑"做对；
- **团队持续采集**：上 Dagster/Prefect 一类编排（DAG 可视化、失败告警）；
- 不管选什么，**存储层统一 + 数据版本工具**都是必需的——编排工具不解决版本问题，版本工具不解决调度问题。

## 四、分步实操：从手工到流水线

### 第 1 步：画当前数据流程图，找出手工断点

把每个环节画成节点，标出：谁触发、输入输出在哪、有没有校验、能不能重跑。常见断点：
- 采集设备 → 服务器：U 盘拷贝/手工上传；
- 转换脚本：本地跑，没进版本库；
- 清洗规则：Excel 里改；
- 训练集切分：人肉选文件夹。

### 第 2 步：先固定"输入输出协议"

为每个环节定义稳定接口：
- 目录/命名规范：`{date}/{batch_id}/{sensor}/{ts}.ext`；
- 元数据文件：每批采集带 `batch.json`（时间、设备、任务书版本、操作者）；
- 产物规范：清洗/转换后必有 `report.json`（规则版本、命中统计）。

> 协议先行，工具后上——没有协议就上调度器，只会把混乱自动化。

### 第 3 步：把每个环节变成"可重跑函数"

每个环节写成一个独立任务，遵守：
- 输入只读，输出写新目录/新版本（**绝不原地覆盖**）；
- 每次运行记录：代码 commit、配置、输入版本、输出摘要；
- 失败即退出并留下日志，由编排器重试或告警。

### 第 4 步：事件驱动与调度

- 采集完成 → 自动触发"同步+体检"（第 2 章实时校验规则复用）；
- 每日定时跑"清洗+去重+评分"增量任务；
- 训练集发布前触发"门禁任务"（质量分、脱敏扫描、切分校验），**门禁不过不出厂**。

### 第 5 步：版本与血缘落地

- 用 DVC（或等价工具）管数据集版本：每个版本一个 commit，记录输入与加工代码；
- 元数据里写 `parent_batch`、`pipeline_version`、`rules_version`；
- 训练实验记录（wandb/MLflow 等）必须引用**数据集版本号**，而不是"最新数据"。

### 第 6 步：监控与告警

| 指标 | 告警场景 |
| --- | --- |
| 环节失败率 | 突然升高 → 查设备/代码变更 |
| 批次质量分趋势 | 完整性/正确性骤降 → 查传感器与标定 |
| 流水线耗时 | 超预期 → 查数据量突增或代码退化 |
| 门禁拦截率 | 突增 → 规则或采集环节变更 |

## 五、核心参数详解

| 项 | 建议基线 | 作用 | 备注 |
| --- | --- | --- | --- |
| 重跑幂等性 | 100% 可重放 | 可复现 | 输出哈希校验 |
| 输出目录 | 新版本目录，绝不覆盖 | 防事故 | 旧版保留可回滚 |
| 增量处理窗口 | 按天/按批次 | 控制成本 | 全量定期重算 |
| 门禁项 | 质量分+脱敏+切分 | 出厂检查 | 见第 4/6/9 章 |
| 血缘记录 | 每产物必填 | 可追溯 | parent + pipeline 版本 |
| 训练引用 | 数据集 commit/版本号 | 实验可复现 | 禁止"最新数据" |

## 六、高频踩坑清单

| 现象 | 根因 | 排查 | 解决 |
| --- | --- | --- | --- |
| 重跑结果不一样 | 环节有隐藏状态/随机性/读旧数据 | 对比两次输出哈希 | 输入只读、固定 seed、版本记录 |
| 新规则没生效 | 清洗脚本没版本化，跑的旧代码 | 查运行日志 commit | 代码入库+运行记录 |
| 训练集混入评测集 | 切分靠人肉 | 查血缘与切分任务 | 切分进流水线，按场景哈希划分 |
| 2TB 数据被覆盖 | 原地写 | 查输出目录历史 | 新版本目录+禁止覆盖 |
| 采集设备断连没人知道 | 无事件监控 | 看告警记录 | 采集→同步自动触发+失败告警 |
| 实验复现不了 | 记录里只写"用最新数据" | 查实验日志 | 强制数据集版本号 |
| 编排器上了更乱 | 环节接口没固定就自动化 | 看 DAG 依赖 | 先统一输入输出协议 |

## 七、进阶优化

1. **数据管道 CI 化**：规则/转换代码走测试（小样本黄金集校验输出），代码合入即自动跑冒烟，防"改坏全库"。
2. **增量 + 定期全量双轨**：日常增量快跑，每周/每月全量重算校验一致性，发现历史 bug 及时重建版本。
3. **训练集发布即制品**：把数据集发布做成与代码发布同级的制品（带签名、数据卡、门禁报告），训练系统只认制品。
4. **成本与存储分层**：原始数据冷存、加工中间产物按需清理、训练集热存——配合血缘，清理不心疼。

## 八、本章 TOP3 核心总结

1. **三原则：幂等、版本化、血缘**——任何产物都能重放、能追溯、能回滚。
2. **先协议后工具**：固定命名/元数据/接口，再上编排调度，避免"把混乱自动化"。
3. **门禁出厂**：质量分+脱敏+切分校验进发布任务，训练集只认带数据卡和版本的制品。

> 📌 记住这一句：**自动化不是为了让流程变快，是为了让错误可以被发现、被修复、被不再犯。**
