## 📌 开篇钩子

Demo 通过、联调完成、机器人正式上岗。第一周客户很满意，第二周开始出幺蛾子：夜间任务失败率悄悄升高没人发现、一次软件升级让 30 台机器集体罢工、某个传感器静默失效三天后才发现——**客户评价从"惊艳"变成"不敢用"只需要一次事故**。

机器人是"运行在物理世界的软件"：它没有"重启大法"的宽容度，也没有"明天再修"的缓冲。稳定性工程要回答的不是"坏了怎么修"（第 42 章），而是**"怎么让坏的影响最小、发现最快、恢复最稳、下次不再犯"**——监控、告警、灰度、回滚、长期验收，一套让系统"敢 7×24 跑"的工程体系。

## 一、章节定位与适用人群

**章节定位**：部署层（从上线到长期运营）。解决的核心问题：**上线后无监控、升级事故无灰度回滚、长期稳定性无验收标准**。

**适用场景**：企业开发 ☑（重点）产品量产适配 ☑（重点）
**建议阅读时长**：14 分钟（建议收藏，机器人交付与运营阶段对照）

**读完你将能**：

3. 用长期验收数据证明"系统稳定"，而不是"感觉稳定"。

## 二、大白话原理：稳定不是状态，是流程

### 2.1 稳定性的三层定义

- **功能稳定**：任务成功率达标（第 30/41 章协议）；
- **运行稳定**：7×24 无故障漂移（内存、温度、延迟）；
- **变更稳定**：每次升级不引入回归（灰度+回滚）。

只测功能稳定就上线的团队，会在运行稳定和变更稳定上栽跟头——**很多事故不是"用坏的"，是"改坏的"**。

### 2.2 三个核心机制

1. **监控**：看得见（指标+日志+告警）；
2. **发布机制**：改得稳（灰度+回滚+版本）；
3. **验收循环**：证明得清（长期数据+复盘改进）。

> 💡 金句：**稳定性工程的目标不是"永远不出事"，而是"出事时损失最小、恢复最快、复盘最全"。**

## 三、分步实操：稳定性体系五步

### 第 1 步：建监控指标体系（分层）

| 层 | 指标示例 | 采集 |
| --- | --- | --- |
| 任务级 | 成功率、节拍、失败模式分布 | 任务日志 |
| 系统级 | 节点状态、延迟 P95、CPU/内存、状态机异常 | 系统遥测 |
| 硬件级 | 温度、电流、电池、编码异常计数、线缆/连接健康 | 硬件监控（第 21/36 章） |
| 环境级 | 现场温度/供电/网络 | 环境传感器 |

每类指标定**基线**（上线前两周统计），偏离基线触发告警——没有基线的告警是噪声。

### 第 2 步：告警分级与响应（别让告警变成"狼来了"）

| 级别 | 例子 | 响应 |
| --- | --- | --- |
| P0 | 安全事件/大面积停摆 | 立即响应+上报 |
| P1 | 任务成功率跌破红线 | 15–30 分钟响应 |
| P2 | 单机异常/指标漂移 | 当日处理 |
| P3 | 趋势预警 | 排期处理 |

**纪律**：每个告警有阈值依据与处理手册；误报率高的告警要修而不是忽略（狼来了效应毁掉整个监控体系）。

### 第 3 步：版本与灰度发布（机器人特有的"发布难"）

机器人升级比云端难：不能"先上 1% 流量"那么简单，但可以分级：
1. **仿真回归**：新版本先在仿真跑回归场景集（第 30/41 章）；
2. **单台试运行**：选 1 台代表机器跑 1–3 天（低风险任务+值守）；
3. **小批灰度**：5–10 台跑一周，对比监控指标；
4. **全量+可回滚**：全量前确认回滚包就绪。

**回滚设计**：软件版本回滚 + 配置回滚 + **模型回滚**（VLA/感知权重也要能回退）；OTA 包带签名与校验，断点续传与失败保护。

### 第 4 步：长期验收（稳定性要用数据说话）

- 目标：如"连续 30 天任务成功率 ≥99%、P1 事故 0 起、无计划外停机"；
- 周报/月报：成功率、故障数、MTBF（平均无故障时间）、MTTR（平均修复时间）；
- **趋势看板**：失败率曲线、漂移曲线——很多故障是"温水煮青蛙"式恶化，趋势比单点告警更早发现问题。

### 第 5 步：事故复盘与改进闭环

每次 P0/P1 事故走复盘：时间线 → 根因（第 42 章方法）→ 改进项（监控/代码/流程/培训）→ 验证 → 归档。**复盘产出必须落到"下次不会发生"的具体改动**，否则复盘只是安慰仪式。

## 四、核心参数详解

| 参数 | 建议起点 | 作用 | 备注 |
| --- | --- | --- | --- |
| 成功率红线 | 业务定（如 99%） | 告警 | 分任务 |
| 基线窗口 | 上线前 1–2 周 | 告警依据 | 随季节/班次修正 |
| 单台试运行 | 1–3 天 | 发布闸门 | 低风险任务 |
| 小批灰度 | 5–10 台/一周 | 统计意义 | 监控对比 |
| 回滚时间目标 | 分钟级 | 事故止损 | 演练过才算数 |
| 复盘时限 | P0 24h / P1 72h | 改进节奏 | 归档案例库 |

## 五、高频踩坑清单

| 现象 | 根因 | 排查 | 解决 |
| --- | --- | --- | --- |
| 告警太多没人看 | 无分级无基线 | 告警统计 | 分级+阈值校准 |
| 升级搞瘫全线 | 跳过灰度 | 变更记录 | 单台→小批→全量 |
| 想回滚发现回不去 | 无回滚包/配置没备份 | 回滚演练 | 版本+配置+模型全可回滚 |
| 温水煮青蛙式恶化 | 只看告警不看趋势 | 趋势看板 | 漂移曲线监控 |
| 事故复复盘复犯 | 改进项没落地 | 跟踪改进项 | 复盘闭环+验证 |
| 模型更新引入回归 | 只回归了软件 | 全量回归 | 模型也走灰度+回滚 |
| 现场网络差 OTA 失败 | 无断点续传 | 升级日志 | OTA 可靠性设计 |
| 监控本身挂了没人知道 | 监控无监控 | 心跳 | 监控自愈+心跳告警 |

## 六、进阶优化

1. **数字孪生运营看板**：把现场机器人的关键指标叠加到数字孪生视图（第 26 章），远程一眼看清全线健康。
2. **自动回滚**：灰度期关键指标跌破红线 → 自动回滚并通知（先小范围试点自动回滚，逐步放开）。
3. **预测性维护运营化**：温度/电流/漂移趋势模型输出"建议保养时间"，把计划外停机变成计划内维护。
4. **SLA 化**：与客户用同一套指标定义服务水平（可用率/成功率/响应时间），稳定性的价值可度量、可签约。

---

## 七、本章 TOP3 核心总结

1. **稳定 = 功能+运行+变更三层稳定**：监控看运行、灰度回滚保变更、长期验收证功能。
2. **告警要分级有基线**：P0–P3 分级+处理手册，趋势看板抓"温水煮青蛙"式恶化。
3. **发布是高风险动作**：仿真回归→单台→小批→全量，软件/配置/模型全部可回滚，复盘改进必须闭环落地。

> 📌 记住这一句：**客户不会为"惊艳的 Demo"续费，只会为"敢 7×24 跑的系统"续费。**
