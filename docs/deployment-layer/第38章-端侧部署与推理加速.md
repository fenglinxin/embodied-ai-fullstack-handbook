## 📌 开篇钩子

训练机上 VLA 推理 300ms，感觉还行。搬到机器人身上：图像采集 15ms + 预处理 20ms + 模型 300ms + 后处理 10ms + 控制链路……**一次决策 400ms**，机器人动作看起来像网络卡顿，抓个移动的杯子全是慢动作。

"能跑"与"能实时跑"之间，隔着部署工程：推理引擎选型、算子融合、显存管理、预处理上设备、流水线并行、尾延迟优化。本章把端侧部署讲成一套方法论：**先剖析再优化、先引擎后算子、延迟与显存分开算账**，让你把模型从"训练机"搬上"机器人本体"时不掉链子。

## 二、大白话原理：推理延迟花在哪？

一次"端到端决策"的延迟 = 采集 + 预处理 + **模型推理** + 后处理 + 通信/调度。模型推理通常是大头，但**预处理与调度往往是被忽略的第二大头**：图像缩放/归一化在 CPU 上做、每帧动态分配内存、线程反复切换——都能偷偷吃掉几十毫秒。

优化顺序（按性价比）：
1. **先测准**：端到端剖析，找到真瓶颈（别优化错地方）；
2. **引擎与格式**：用目标硬件的推理引擎（算子融合/图优化白赚 2–5 倍）；
3. **管线并行**：采集/预处理/推理/后处理流水化，隐藏延迟；
4. **资源管理**：显存复用、线程亲和、尾延迟治理。

> 💡 金句：**部署优化的第一定律：先测量，再优化——90% 的"优化"都在优化一个不是瓶颈的地方。**

## 三、选型对比：推理引擎怎么选？

| 引擎 | 强项 | 注意 |
| --- | --- | --- |
| TensorRT（NVIDIA GPU） | 图优化+算子融合+INT8，性能标杆 | 绑定 NVIDIA、构建时间长 |
| ONNX Runtime | 跨平台/多硬件、生态好 | 性能取决于 EP（执行提供方） |
| OpenVINO | Intel CPU/iGPU/NPU 优化 | 绑定 Intel |
| TFLite/MediaPipe 类 | 移动/嵌入式轻量 | 大模型支持弱 |
| 厂商 NPU SDK（如 RKNN 等） | 端侧 NPU 峰值 | 算子支持有限、按厂商 |
| llama.cpp/GGUF 类 | LLM/VLA 社区生态 | 面向文本/通用，按需评估 |

**选型结论**：先看目标硬件与模型类型——NVIDIA 平台 TensorRT 优先；跨平台 ONNX Runtime；端侧 NPU 用厂商 SDK；**评估标准只有一个：在你的硬件+模型+批大小上实测 P50/P95**。

## 四、分步实操：端侧部署六步

### 第 1 步：端到端剖析（半天，必做）
- 把采集→预处理→推理→后处理→发布拆段计时，跑 1000 次统计 P50/P95/max；
- 同时记录：显存/内存峰值、CPU 占用、线程切换；
- 输出"延迟瀑布图"：哪段占多少、哪段抖动大——**这就是优化清单**。

### 第 2 步：选引擎与导出格式
- 模型导出：PyTorch→ONNX（固定/动态轴按需）→目标引擎（TensorRT 等）；
- 检查算子支持：不支持的算子找替代/拆子图（引擎日志会报）；
- 精度验证：引擎输出 vs 原模型输出误差在容差内（第 24 章纪律：导出后必跑黄金评测）。

### 第 3 步：预处理与后处理上设备
- 图像缩放/归一化/颜色转换放到 GPU/NPU（TensorRT 预处理或 CUDA 前处理）；
- 后处理（NMS 等）用目标硬件加速库或轻量实现；
- **避免每帧 Python 层反复拷贝**：用固定 buffer/异步拷贝。

### 第 4 步：管线并行与异步
- 采集线程 / 推理线程 / 控制线程解耦，用队列+双缓冲；
- 推理用异步 API：上一帧推理时同时采下一帧；
- 延迟预算里区分"单次推理延迟"与"端到端吞吐"——机器人要的是前者可控。

### 第 5 步：资源与稳定性
- 显存/内存：显存池复用（避免每帧分配）、必要时限帧率；
- 线程：推理线程钉核、优先级合理（与第 37 章实时设计衔接）；
- 预热：部署启动时跑几次推理完成算子/内存预热，避免首帧超慢；
- 长跑验收：连续运行数小时，延迟 P95 不漂、显存不涨（泄漏检查）、温度不降频。

### 第 6 步：整机联调验收
- 在真实负载（感知+规划+控制全开）下测端到端延迟预算达成率；
- 掉帧/超时策略验证：推理超时 → 用上一帧结果/降级动作（与第 37 章失效安全一致）；
- 记录部署配置版本（引擎版本/精度/批大小），与训练实验绑定（第 11/12 章版本思想）。

## 六、高频踩坑清单

| 现象 | 根因 | 排查 | 解决 |
| --- | --- | --- | --- |
| 引擎比原框架还慢 | 算子不支持走 fallback | 看引擎日志 | 换算子/拆图/换引擎 |
| 首帧慢 10 倍 | 没预热/动态分配 | 首帧计时 | 启动预热 |
| 显存越跑越高 | 每帧分配不释放 | 长跑监控 | 显存池复用 |
| 延迟平均好偶尔爆 | 线程调度/GC/降频 | P99 分析 | 钉核/锁内存/散热 |
| 预处理吃掉一半延迟 | 在 CPU 上做 | 瀑布图 | 预处理上设备 |
| 导出后结果漂了 | 精度损失/算子差异 | 输出对比 | 精度验证+敏感算子保留高精度 |
| 只优化模型不管链路 | 无端到端剖析 | 瀑布图 | 全链路优化 |
| 一满载就超时 | 无超时策略 | 负载测试 | 掉帧策略/降级（第 37 章） |

## 七、进阶优化

1. **多模型共享引擎上下文**：感知+VLA 等多个模型共用 TensorRT 上下文/显存池，减少切换开销（机器人常同时跑多个模型）。
2. **动态批处理与执行计划分层**：在线固定批 1 保延迟，离线/批量任务用动态批保吞吐。
3. **模型-引擎联合编译**：蒸馏/剪枝后直接面向目标引擎做"精度-速度"联合搜索（AutoML 部署），量产时按型号出包。
4. **远程"部署实验室"**：在真实负载+最差环境（高温/满载）下做部署回归，每次模型更新跑同一套延迟与精度验收。

## 八、本章 TOP3 核心总结

1. **先剖析后优化**：端到端瀑布图定位真瓶颈，预处理/调度常常和模型一样值得优化。
2. **引擎按硬件选、按实测定**：TensorRT/ONNX Runtime/厂商 SDK 各有所长，P50/P95 实测说了算。
3. **资源与稳定性是量产红线**：显存池复用、预热、线程钉核、长跑 P95 不漂；超时必须有降级策略。

> 📌 记住这一句：**端侧部署的本质是"把每一毫秒的账算清楚"——算清了，模型才真正属于这台机器人。**
